Hardware is [validated](/blog/homelab-validation/hardware). Network is [configured](/blog/homelab-network-impl/phase0). Time to see if OKD actually works on this thing.

This is Stage 0: a Single Node OpenShift (SNO) deployment of OKD 4.20 on Node 4. No quorum, no distributed storage, no LACP bonding. The goal is to confirm platform-level functionality — OKD bootstrap, operator health, console access, monitoring, and Backnet storage path — before committing to a 3-node cluster.

<Callout title="Scope" variant="summary">
  - **In:** OKD 4.20 SNO on Node 4, agent-based install, full operator and monitoring validation, Backnet L2/L3 path test.
  - **Out:** Rook-Ceph (needs 3+ nodes), LACP bonding (deferred to Phase 1), production workloads.
  - **Duration:** ~3–4 hours (install: ~1 hour, validation: ~2–3 hours).
</Callout>

## Prerequisites

### Network

The [Phase 0 MikroTik config](/blog/homelab-network-impl/phase0) must be deployed before the node boots. The specifics are covered there — DHCP on Frontnet, static lease for Node 4 at `192.168.1.7`, Backnet interface at `192.168.10.1/24`, inter-VLAN firewall, NAT, and VLAN filtering on both devices.

### DNS

For SNO with `platform: none`, the API and ingress bind directly on the node — there are no separate VIPs managed by keepalived. I pointed all OKD DNS records straight at the node IP:

```routeros
/ip dns static
add name=api.sno.home.lab address=192.168.1.7
add name=api-int.sno.home.lab address=192.168.1.7
```

```routeros
/ip dns
set allow-remote-requests=yes
```

For the wildcard `*.apps.sno.home.lab`, RouterOS uses a regex forward rule pointing to the node IP.

Verify from your workstation:

```bash
dig +short api.sno.home.lab @192.168.1.1
# 192.168.1.7

dig +short test.apps.sno.home.lab @192.168.1.1
# 192.168.1.7
```

![DNS verification — api and apps wildcard both resolving to 192.168.1.7 via router and Pi-hole](./sno-dns-verify.png)

Both the router (`@192.168.1.1`) and Pi-hole (`@192.168.1.12`) return `192.168.1.7`. RouterOS evaluates its static entries before forwarding, so Pi-hole doesn't need OKD-specific records.

<Callout title="If DNS fails" variant="warning">
  Check `/ip dns static print` on the router. Records must exist and not be disabled. Also verify DNS is accepting remote queries: `/ip dns print` should show `allow-remote-requests: yes`.
</Callout>

### Pull secret and SSH key

OKD uses `quay.io/okd/scos-release`. Some operators may pull from `registry.redhat.io`, so include those credentials if you have them.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/okd-homelab -C "okd-homelab"
```

## Installation

### install-config.yaml

```yaml
apiVersion: v1
baseDomain: home.lab
metadata:
  name: sno
compute:
  - name: worker
    replicas: 0          # SNO — no separate workers
controlPlane:
  name: master
  replicas: 1            # Single node
networking:
  networkType: OVNKubernetes
  clusterNetwork:
    - cidr: 10.128.0.0/14
      hostPrefix: 23
  serviceNetwork:
    - 172.30.0.0/16
  machineNetwork:
    - cidr: 192.168.1.0/24    # Frontnet
platform:
  none: {}
pullSecret: '<your-pull-secret-json>'
sshKey: '<your-ssh-public-key>'
```

<Callout title="metadata.name matters for DNS" variant="danger">
  The `metadata.name` becomes the cluster name in all DNS records: `api.<name>.home.lab`, `*.apps.<name>.home.lab`. I initially used `name: okd` — the installer generated configs for `api.okd.home.lab`, but my router DNS pointed at `api.sno.home.lab`. The install timed out after an hour waiting for the API to initialize. The fix was trivial: either change DNS records to match, or change the config name. I changed to `name: sno` to match the existing DNS.
</Callout>

### agent-config.yaml

```yaml
apiVersion: v1beta1
kind: AgentConfig
metadata:
  name: sno
rendezvousIP: 192.168.1.7
hosts:
  - hostname: sno.home.lab
    role: master
    interfaces:
      - name: enp0s31f6
        macAddress: D0:8E:79:05:37:0A
    networkConfig:
      interfaces:
        - name: enp0s31f6
          type: ethernet
          state: up
          ipv4:
            enabled: true
            address:
              - ip: 192.168.1.7
                prefix-length: 24
            dhcp: false
          ipv6:
            enabled: false
      dns-resolver:
        config:
          server:
            - 192.168.1.12
      routes:
        config:
          - destination: 0.0.0.0/0
            next-hop-address: 192.168.1.1
            next-hop-interface: enp0s31f6
```

<Callout title="CX4121C interfaces are intentionally left out" variant="note">
  For SNO, Frontnet (onboard NIC) handles all traffic. The Backnet interface gets configured manually post-install for L2/L3 path validation only.
</Callout>

### Generate the agent ISO

I ran the installer from a Podman container on my workstation — avoids needing `nmstate` and the exact `oc` version installed locally:

```bash
sudo podman run --rm -it -v $(pwd):/work -w /work fedora:latest bash -c '
  dnf install -y nmstate tar gzip &&
  curl -sL https://github.com/okd-project/okd/releases/download/4.20.0-okd-scos.17/openshift-client-linux-4.20.0-okd-scos.17.tar.gz \
    | tar xz -C /usr/local/bin &&
  oc adm release extract --command=openshift-install \
    quay.io/okd/scos-release:4.20.0-okd-scos.17 &&
  cp install-config.yaml agent-config.yaml install/ &&
  ./openshift-install agent create image --dir install --log-level=debug
'
```

Output: `install/agent.x86_64.iso` (882 MB). The container also generates `install/auth/kubeconfig` and `install/auth/kubeadmin-password`.

### Monitor installation

From a separate terminal, watch the installer progress:

```bash
./openshift-install agent wait-for bootstrap-complete --dir install --log-level=debug
```

The installer connects to the rendezvous host via SSH, runs host validations (CPU, RAM, disk, platform compatibility, DNS resolution), and starts the install:

![Split screen — JetKVM console on the left, installer progress on the right showing host validations passing](./sno-install-progress.png)

The host validations passed cleanly — one temporary NTP warning that self-resolved:

```

INFO Cluster is ready for install
```

Bootstrap completed in about 33 minutes:

```

```

Then `wait-for install-complete` takes over, progressing through operator initialization. This part took longer — cluster operators cycle through unavailable states as they come up one by one.

<Callout title="Ingress operator timeout" variant="warning">
  The installer timed out at 40 minutes with `Cluster operator ingress is degraded`. The ingress canary route checks were failing — the canary pod at `canary-openshift-ingress-canary.apps.sno.home.lab` was timing out. The cluster was otherwise functional. I let the installer timeout and proceeded with manual validation.
</Callout>

<Callout title="Ingress canary degradation" variant="note">
  The ingress operator reports Degraded=True because `CanaryChecksSucceeding=False`. This is a known pattern on SNO — the canary check creates a route to `canary-openshift-ingress-canary.apps.sno.home.lab` and expects a response within a timeout. On a single node under load from initial operator reconciliation, these checks can timeout without indicating an actual ingress problem. I accepted this as a non-blocking issue.
</Callout>

{"level":"warn","msg":"apply request took too long","took":"206.573733ms","expected-duration":"200ms","prefix":"read-only range "}

These are read-only range requests, not write fsyncs. They happened during initial operator reconciliation when the API server was under heavy load. No persistent fdatasync warnings, no write latency issues. The S3610 is doing its job.

<Callout title="Why etcd performance matters here" variant="important">
  etcd fsyncs on every Kubernetes API change. The Intel D3-S3610 (MLC) was chosen specifically for this workload. Persistent slow warnings here mean the boot SSD can't keep up — and it'll only get worse with a 3-node cluster writing to quorum. A few transient read slowdowns during initial reconciliation are acceptable.
</Callout>

### Backnet (VLAN 10) — storage path validation

The critical pre-Phase 1 test. Prove that the CX4121C port can reach the Backnet gateway (`192.168.10.1`) through the CRS317 switch and CCR2004 router.

```bash
[core@sno ~]$ MLX_IFACE=enp1s0f0np0
[core@sno ~]$ sudo ip addr add 192.168.10.2/24 dev $MLX_IFACE
[core@sno ~]$ sudo ip link set $MLX_IFACE up
[core@sno ~]$ sudo ethtool $MLX_IFACE | grep -E "Speed|Link"
	Speed: 10000Mb/s
	Link detected: yes
```

10 Gbps link, CX4121C on CRS317 sfp-sfpplus2 with pvid=10.

```
[core@sno ~]$ ping -c 5 -I $MLX_IFACE 192.168.10.1
PING 192.168.10.1 (192.168.10.1) from 192.168.10.2 enp1s0f0np0: 56(84) bytes of data.
64 bytes from 192.168.10.1: icmp_seq=1 ttl=64 time=0.153 ms
64 bytes from 192.168.10.1: icmp_seq=2 ttl=64 time=0.118 ms
64 bytes from 192.168.10.1: icmp_seq=3 ttl=64 time=0.084 ms
64 bytes from 192.168.10.1: icmp_seq=4 ttl=64 time=0.122 ms
64 bytes from 192.168.10.1: icmp_seq=5 ttl=64 time=0.109 ms

--- 192.168.10.1 ping statistics ---
5 packets transmitted, 5 received, 0% packet loss, time 4122ms
rtt min/avg/max/mdev = 0.084/0.117/0.153/0.022 ms
```

Sub-millisecond latency, zero packet loss. The full path works: CX4121C → CRS317 (VLAN 10 untagged on sfp-sfpplus2) → trunk (VLAN 10 tagged on sfp-sfpplus1) → CCR2004 (vlan10-backnet interface at 192.168.10.1).

<Callout title="This is a Phase 1 gate" variant="danger">
  If the Backnet path doesn't work here, Ceph replication traffic won't flow in the multi-node cluster. Fix it now.
</Callout>

## What comes after Stage 0

With a GO from SNO validation:

1. **Tear down SNO** — Node 4 becomes part of the 3-node cluster. The SNO installation gets wiped.
2. **Revert DNS** — point records back from `sno.home.lab` to the multi-node cluster name and VIP addresses.
3. **Procure Nodes 5–6** — identical hardware (Dell OptiPlex 5090 SFF with CX4121C).
4. **Run hardware validation on each new node** — same Stage -1 process.
5. **Incremental network upgrades** — enable CRS317 ports for new nodes, create LACP bonds, enable jumbo frames after bonds are stable.
6. **Deploy Phase 1** — 3-node OKD cluster with Rook-Ceph distributed storage.
